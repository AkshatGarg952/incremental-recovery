# Incremental Recovery Engine

**Track 03 — AI Revenue Recovery · Razorpay AI Buildathon**

## The problem

A payment fails. Most recovery systems retry it on a fixed schedule and
report whatever eventually lands as "recovered revenue" — including every
customer who would have paid anyway, on their own, with no intervention at
all. That gross number is a misleading metric: it takes credit for money the
system never actually added.

This project builds a recovery agent that decides *whether*, *when*, and
*how* to intervene on a failed payment — and then measures how much it
actually added, using a randomised holdout arm (nothing happens) **and** a
randomised baseline arm (the fixed retry schedule a merchant already runs).
The number this project stands behind is lift over that baseline, not lift
over doing nothing, and not gross recovery.

```
lift_vs_nothing  = rate(agent) - rate(holdout)    the honesty story
lift_vs_baseline = rate(agent) - rate(baseline)   THE HEADLINE — what a
                                                   merchant doesn't already have
```

## Headline result

**This README does not print a batch-report lift number, on purpose.**
`uv run python tasks.py batch --n 3000 --seed 20260901` produces one — every
figure it prints comes from that exact command against the committed seed,
nothing hand-picked — but generating it needs a full run against live
Gemini/Groq free-tier keys (~1,860 calls, BUILD.md R9), and free-tier daily
quota ran out partway through three live attempts made while finishing this
project, on top of the calls already spent validating the classifier for
real (see below). Printing a number here that wasn't actually produced by
that command, on this seed, would be exactly the kind of unverified claim
this project exists to call out. Run the command yourself — the report
format is documented in full in `skills/batch-report/SKILL.md`, including
what each section means and the "vs baseline" vs "vs holdout" distinction
that's the actual headline.

What *is* real, already measured, and included in this repo:

- **Classifier accuracy on the golden set: 76.7% (23/30)**, `gemini-2.5-flash-lite`,
  live, from `evals/golden_set.jsonl` — a 53.3% LLM-call rate and a 6.7%
  exception rate alongside it. Reproduce with `run_classifier_eval` (see
  `src/agent/classifier_eval.py`).
- **`FAILURES.md`** — five real, diagnosed cases, including one live
  classify call that got a case wrong feeding straight into a live policy
  call, showing the concrete downstream consequence (an unnecessary
  customer contact) rather than just a mislabeled report row.
- The full offline test suite (`uv run pytest`, ~135 tests, ~10s) — every
  build gate in `CLAUDE.md`'s table, including the two that most directly
  back the headline claim: the baseline-invariant check (a fixed retry
  schedule can't underperform doing nothing) and the restraint gate (a
  maximal-contact strategy recovers more gross revenue and still loses on
  net).

## How to run

```bash
uv sync                                 # Python 3.11+, uv
cp .env.example .env                    # fill in GEMINI_API_KEY, GROQ_API_KEY
uv run pytest                           # full suite, offline, ~15s — no API calls
uv run python tasks.py batch --n 3000 --seed 20260901
```

Both API keys are free-tier (Gemini and Groq both offer one). The batch
command needs them; the test suite does not — every test runs against
`FakeProvider`, offline, and burns zero quota.

**First run is slow, repeat runs are instant.** A full `n=3000` batch is
~1,860 LLM calls (BUILD.md R9) and takes 45-90 minutes at free-tier rate
limits the first time. Every classify/policy call is cached by `(role,
provider, model, prompt_version, sha256(payload))`
(`src/llm/cache.py`), so re-running the *same* `n`/`seed` makes zero new
network calls and reports identically in seconds. To skip the wait
entirely, prewarm ahead of time:

```bash
uv run python -m src.perturb.cli prewarm --limit 500
```

To see the live re-plan demo — inject an issuer outage and watch the
agent's decisions change for the affected slice:

```bash
uv run python -m src.perturb.cli outage --issuer HDFC --outage 45m
```

## What's simulated

**No real payment integration exists anywhere in this repository.** There is
no Razorpay test-mode call, no real SMS/email/WhatsApp send, and no real
customer. Specifically:

- `PaymentFailure` records — decline codes, raw issuer messages, customer
  history — are generated by `src/simulator`, calibrated to public decline-code
  distributions (BUILD.md R1), not pulled from any real transaction log.
- Whether a customer "recovers" is decided by `src/simulator/latent.py`, a
  hand-set probabilistic model (self-recovery rate, responsiveness to
  retry/message, fatigue and churn past a contact threshold) — not a real
  customer's real behavior.
- "Sending" a message renders a template to a log line
  (`src/executor/agent_executor.py`); no message ever leaves the process.
- The 7-day recovery horizon runs on a simulated clock
  (`src/executor/clock.py`) that advances only when the code asks it to.

This means the report is **synthetic end to end** — every number in it is a
statement about how this agent performs against this simulator, not a claim
about production payment behavior. The specific things that make the
simulator a fair test rather than a rigged one: recovery-class ground truth
is fixed before the agent's code exists, the generator distribution is
committed and inspectable (`data/reference_batch.jsonl`,
`data/DISTRIBUTION_SUMMARY.md`), and the holdout-vs-baseline design measures
the agent against a fixed schedule, not against nothing. It does not make
the numbers real. Section "Panel answers" in `docs/BUILD.md` covers the
sharper version of this question if it comes up.

## Compliance disclaimer

`config/envelope.yaml`'s numbers (retry caps, quiet hours, contact frequency)
are this project's best reading of public guidance — RBI's e-mandate
circulars and TRAI's commercial-communication rules — for a hackathon
prototype. **This is not legal advice, and none of it has been reviewed by
counsel.** Every number is in config, with a provenance comment, specifically
so it can be corrected by someone qualified rather than trusted as fact. Real
production caps come from NPCI/scheme rules and merchant agreements, not this
repository.

## Architecture, in one line

The LLM proposes, deterministic code disposes. A classifier and a policy
agent call an LLM only where a rule can't already tell (rule prior handles
~clean decline codes for free; the policy agent proposes retries and
messages); everything either produces is then bound by a fully deterministic
envelope (`src/envelope`) before anything executes. Worst case — the model
is down, or returns garbage — the envelope blocks and the batch falls back
to baseline behaviour and still reports. See `CLAUDE.md` for where
everything lives and the one invariant (`src/agent`, `src/envelope`,
`src/executor` never see ground truth) the whole measurement depends on.
